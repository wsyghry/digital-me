# 决策记录 · 分身志

> 记「定了什么」和「为什么」，不记过程。有新结论往下追加，旧结论不删，改主意就标注被哪条取代。

---

## D1 · 产品定位：一个底座，三个出口

**结论**：不做三套系统。数据只存一份，向上接三个能力：检索、时间线、分身对话。分身作为主入口，检索和时间线是它的支撑。

**理由**：三者共用同一份清洗后的语料，分成三套会重复做三次清洗，而且三份数据会漂移。分身 = 人格层（怎么说）+ 记忆层（知道什么），记忆层就是检索，所以本质是一件事的三个面。

**已知取舍**：主入口给分身，意味着把那部分不确定性放在最前面。缓解方式是把人格层先做成提示词，不依赖微调。

---

## D2 · 平台边界：不碰微信/QQ 协议

**结论**：不接入微信个人号协议、不做 hook、不做自动化收发。微信侧只做「拟好草稿，人确认后自己发」。

**理由**：微信个人号没有官方 API，任何自动收发都是外挂，违反平台协议且有封号风险；以本人身份自动回复还可能构成冒充。QQ 官方机器人只能以机器人身份存在，同样无法顶替本人。

**替代路径**：对外提供时走企业微信「微信客服」，用户无需加好友即可进入服务窗口，有官方 API。需要企业主体（个体户营业执照即可）。

---

## D3 · 数据托管：整库留在自己手里

**结论**：语料存储与检索都在用户自有的机器/服务器上。只有「提问文本 + 检索命中的少量片段」会发送给模型 API。

**理由**：语料里一半以上是他人说的话，整库外流等于把朋友的隐私托管给第三方。个人使用场景下，这个风险没有收益可换。

**代价**：需要一台 24 小时在线的机器，或接受「电脑开着才能用」。

---

## D4 · 技术栈：Python + FastAPI + SQLite + 免构建前端

**结论**：后端 Python 3.12 + FastAPI；存储用 SQLite 单文件 + FTS5 全文索引；前端单页、无打包工具；模型走 DeepSeek API。

**理由**：
- 单人使用、数据量在十万条以内，SQLite 完全够，省掉数据库运维和迁移成本
- FTS5 的 trigram 分词可做中文子串检索，无需额外分词器；但它对少于 3 个字符的查询匹配不到（实测 SQLite 3.43.1），所以检索层要留一条 `LIKE` 兜底路径给「明天」「老王」这类两字词，这是已知代价，不是遗漏
- 无构建步骤的前端，改完刷新即可，减少调试链路
- 本机无独显，模型推理只能走云 API，这一点没有选择余地

**已经排除**：Docker（机器上没装、也没 WSL，先不引入）、Postgres（MVP 阶段过度设计）、向量数据库（先用 FTS，等检索质量不够再加）。

---

## D5 · 部署路径：先本机跑通，再上云

**结论**：P1~P3 在本机完成，验证后才买服务器。服务器候选为香港轻量 2 核 2G（免备案）。

**理由**：真正的难点是数据清洗与检索质量，不是部署。本机阶段零成本、改代码即时生效；迁到云上时只需搬 `me.db` 一个文件。

**待定**：大陆地域需 ICP 备案（1~20 天），香港免备案但延迟略高。域名与备案情况尚未确认。

---

## D6 · 命名

**结论**：项目名「分身志」，英文标识 `digital-me`，目录 `D:\agent\digital-me`。

**理由**：「分身志」延续个人网站「个人志」的命名，「志」能同时容纳记录、检索、回忆，不被「分身」一词限制；目录用 ASCII，避开 Python 虚拟环境与 pip 在中文路径下的偶发问题。

---

## D7 · 版本管理：双远程，按功能节点提交

**结论**：每完成一个可验收的功能就提交一次，同时推到 gitee 和 github 两个远程。

- 远程名固定 `gitee` / `github`，两个都推，不设默认只推一个
- 提交信息用 Conventional Commits 前缀（`feat` / `fix` / `docs` / `chore` / `refactor`），描述用中文写清改了什么
- 提交粒度跟着验收节点走：一个功能能跑、能被看见，就提交一次。不攒着一起交
- 推送成功要回报两个远程各自的结果，不能只报一个

**理由**：这是要长期维护的个人项目，出问题时需要一个能回退的点。国内访问 github 时好时坏，gitee 是备份也是日常可访问的那份。

**注意**：`.env`、`data/`、`.archify/` 不进仓库（见 `.gitignore`）。数据永远只在本地和以后的服务器上，不上代码托管。
