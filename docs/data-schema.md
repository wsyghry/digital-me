# 数据结构 · 分身志

> 一份 SQLite 文件 `data/me.db`。建表语句的唯一出处是 `app/db/schema.sql`，本文件只解释「为什么这么设计」。

---

## 设计原则

1. **一条记录 = 一句话**，不分来源。微信的、QQ 的、你手机里随手记的，都进同一张 `messages` 表，用 `source` 区分。
2. **时间、来源、谁说的、在哪说的**，这四件事必须齐全，否则以后没法做时间线和人物消歧。
3. **原文不动**。清洗只做「去掉无效行」，不改写内容。改写留在检索和展示层，原文永远是证据。
4. **去重靠指纹**，不靠唯一自增。同一条消息被导出两次不能变成两条。

---

## 表：messages

核心表，所有语料都在这里。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER 主键 | 自增 |
| `ts` | TEXT | 发生时间，ISO 8601 带时区，如 `2021-06-01T21:30:00+08:00` |
| `source` | TEXT | `wechat` / `qq` / `note`（随手记）/ `import`（其他补充） |
| `conv` | TEXT | 会话名：好友昵称、群名。随手记为 NULL |
| `sender` | TEXT | 发送者显示名。自己发的存 `me` |
| `is_me` | INTEGER | 1 = 我发的，0 = 别人发的 |
| `text` | TEXT | 正文。图片/文件/位置等存占位描述，如 `[图片]` |
| `kind` | TEXT | `text` / `image` / `file` / `voice` / `card` / `system` |
| `fp` | TEXT UNIQUE | 指纹：`ts + source + conv + sender + text` 的 SHA1，去重用 |
| `created_at` | TEXT | 入库时间，用于排查导入批次 |

**索引**：`ts`（时间线）、`source`（按来源筛）、`conv`（按会话筛）、`is_me`（只搜我自己说的话时用）。

### 为什么 `is_me` 单独存一列

分身要像你，最关键的是「你自己怎么说话」。每次训练语气样本、抽人格示例，第一条件就是 `is_me = 1`。把它做成索引列，比每次比对昵称可靠——你在不同群里用的昵称不一样。

| `id` | INTEGER 主键 | |

P1 阶段可以先只有这一张空表，等真导入历史记录时再往里填。检索时命中的 `sender` 若能映射到 `persons`，展示时优先显示首选称呼。

## 全文索引：messages_fts

用 SQLite 内置 FTS5，`tokenize = 'trigram'`，external content 模式（`content='messages'`）——索引里不再存一份正文，靠 `messages` 上的 insert / delete / update 三个触发器保持同步。

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
  text, conv, sender, content='messages', content_rowid='id', tokenize=trigram
);
```

**为什么用 trigram 而不是默认分词**：中文没有空格，默认 tokenizer 会把一整句当成一个词，搜「老地方」命中不了「明天在老地方见」。trigram 把文本切成三字滑动窗口，能命中句中任意位置。

**它的硬限制（已实测，SQLite 3.43.1）**：查询串少于 3 个字符时，trigram 一条都匹配不到——`搜「明天」→ 0 条`，尽管库里明明有。而中文两字词极常见（明天、上午、九点、老王），所以检索必须分两路：

| 查询长度 | 走哪条路 | 实测耗时（10 万条） |
|---|---|---|
| ≥ 3 字 | FTS5 MATCH | 约 0.1 ms |
| 1~2 字 | `LIKE '%词%'` 全表扫 | 约 15 ms |

两字查询慢一百倍，但绝对耗时 15 ms，人感觉不出来，不必为它再引一套分词器。

### 查询串怎么拼（踩过的坑，已实测）

用户输入不能直接塞进 `MATCH`，否则特殊字符会让 SQLite 直接抛 `unterminated string`。规则：

1. 按空白把输入切成若干词。
2. 每个词用双引号包成短语：`"老地方"`，词内的 `"` 再写一遍转义。短语还能接受含单字/两字的词（`"3 号柜"` 能命中），裸写不行。
3. ≥3 字的词进 `MATCH`，多个词用 `AND` 连；不足 3 字的词不参与 MATCH，改用 `LIKE '%词%'` 对结果再筛。
4. 全是短词，或输入为空 → 直接走 `LIKE`。

两个容易误解的地方：裸写 `明天 老地方` 时 SQLite 会**默默丢掉**两字词，只按「老地方」检索，看起来命中其实少了一个条件；短语写法 `"明天 老地方"` 则要求原文里真有这个空格。所以短词必须走 LIKE，不能指望 FTS 兜。

**为什么先不上向量检索**：FTS 已经能覆盖「记得大概用词」的场景，而向量库要额外依赖和调参。等实际用起来发现「我知道有这事但想不起用词」搜不到时再加，那时才知道该用什么 embedding。

## 导入格式（jsonl）

一行一条，UTF-8，字段与 `messages` 表对应：

```json
{"ts":"2021-06-01T21:30:00+08:00","source":"wechat","conv":"老王","sender":"me","is_me":1,"text":"明天几点","kind":"text"}
{"ts":"2021-06-01T21:31:12+08:00","source":"wechat","conv":"老王","sender":"老王","is_me":0,"text":"九点行吗","kind":"text"}
```

规则：
- `ts` 必填，统一转成带时区的 ISO 格式，不带时区的一律按 `+08:00` 处理
- `fp` 由导入脚本算，不用手填
- 同 `fp` 的行直接跳过，不报错——重复导入是常态
- 缺 `conv` 可以（随手记），缺 `ts` 或 `text` 该行丢弃并计入报告

导入脚本最后输出一份报告：总行数 / 新增 / 跳过重复 / 丢弃及原因 / 时间跨度 / 各来源条数。

## 随手记的特殊处理

手机端记的一句话，和微信消息结构一样，只是：

- `source = note`
- `conv = NULL`、`sender = me`、`is_me = 1`
- `kind = text`

好处是检索、时间线、人格样本三处逻辑完全不用为它写分支。

## 数据量与性能

以下为实测值（Python 3.12.2 + SQLite 3.43.1，10 万条短句，平均约 35 字）：

| 指标 | 实测 |
|---|---|
| 库体积（含全部索引） | 26.5 MB |
| 全量建库 + 建索引 | 0.8 秒 |
| FTS 查询（≥3 字） | 约 0.1 ms / 次 |
| 两字查询（LIKE 兜底） | 约 15 ms / 次 |

一条消息平均只占约 270 字节，十万条以内 SQLite 毫无压力。真实微信文本比测试短句更短，体积只会更小。真到五十万条以上再考虑分库或迁 Postgres。

## 备份

`data/me.db` 一个文件就是全部。备份方式：

- `scripts/backup.ps1` 拷到指定目录，文件名带日期
- 或直接手动复制——前提是先停服务，避免拷到写入中的文件

不在备份里的是 `.env`（含密钥），那个自己另存。
