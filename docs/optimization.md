# 优化清单 · 分身志

> 这份文件回答：**哪里还能更好，值不值得现在做。**
> 用法见 [usage.md](usage.md)，文件分工见 [modules.md](modules.md)。

每一条都写四件事：**现状 → 做法 → 代价 → 什么时候值得做**。

有一条总原则：**先做完，再做好。** 现在（P0/P1）任何优化都还没有真实数据支撑，做了也是猜。等有几千条自己的记录、用上一两个月，才知道痛在哪。

---

## 一、检索质量（最值得投入的地方）

### 1.1 两字词只走全表扫

- **现状**：FTS5 trigram 对 ≤2 字符的查询返回 0 条，只能退到 `LIKE '%词%'` 全表扫，10 万条约 15 ms。
- **做法**：建一张「二元组索引表」——把每条正文拆成相邻两字的组合（`老王`、`王说`、`说好`…），单独建 FTS 或普通索引表，两字查询查它。
- **代价**：库体积涨约 1.5 倍，写入变慢，需要重写检索拼装逻辑。
- **什么时候做**：当你发现自己在反复搜两字词（比如总搜「老王」「报销」），且记录量过了十万条、15 ms 变成能感觉到的卡顿。十万条以内，别做。

### 1.2 换个说法就搜不到

- **现状**：纯字面匹配。搜「郁闷」搜不到「心情不好」。
- **做法**：加语义检索——用一个 embedding 模型把每条记录转成向量存起来（`sqlite-vec` 扩展可以继续用 SQLite 一个文件，不用引独立向量库），查询时字面结果 + 语义结果混合排序。
- **代价**：要引入 embedding 调用（每条记录一次，导入历史时是几万次）、向量存储、混合排序调权重。都是新依赖。
- **什么时候做**：明显感觉到「我知道记过，但想不起原话」的情况超过每周一两次。这是唯一值得为检索引入 AI 的地方。

### 1.3 按条检索，答非所问

- **现状**：搜到的是单条消息，上下文割裂——「九点行吗」单拎出来不知道在说什么。
- **做法**：按「话题段」分块——同一会话里时间相近（如 30 分钟内）的连续消息合成一段再入库或再检索，返回时带前后文。
- **代价**：要定「多近算一段」的规则（不同会话节奏不同），并为分块后的数据重做索引。属于 P3 导入历史时才划算的改造。
- **什么时候做**：导入历史记录后，发现检索结果经常断章取义。

### 1.4 排序：只按时间倒序

- **现状**：结果按时间倒序，越新越前。
- **做法**：相关性（FTS 的 BM25 分数）× 时间衰减，混合排序；同一会话的结果聚在一起。
- **代价**：要调两个权重，调不好反而更差。
- **什么时候做**：记录上万条后，搜一个词出来几十条、翻半天找不到想要的那条时。

### 1.5 人物消歧没做

- **现状**：`persons` 表先留空，同一个人在不同群的不同昵称是不同字符串。
- **做法**：别名归并——人工确认 + 规则（备注名、头像哈希、同会话高频共现）。**这一步没有全自动的好办法，人工确认是必须的。**
- **代价**：导入历史后期，要花半天对着一张别名表点头。
- **什么时候做**：P3 导入历史时一起做，早做没意义（没数据）。

## 二、速度

### 2.1 单条写入每条都开事务

- **现状**：随手记是低频操作，一条一个事务完全没问题。
- **做法**：导入历史时用批量事务（每 500~1000 条提交一次），配 `PRAGMA journal_mode=WAL`、`synchronous=NORMAL`。
- **代价**：几乎为零，P1 就顺手开 WAL。
- **什么时候做**：P1 建库时就开；批量事务在写 `import_jsonl.py` 时做（P3）。

### 2.2 分页用 OFFSET

- **现状**：列表可能一次查很多条。
- **做法**：按 `id` 或 `ts` 做 keyset 分页（`WHERE ts < 上一页最后一条`），不用 `OFFSET`。
- **代价**：前端要记游标，十行代码的事。
- **什么时候做**：P1 就按 keyset 写，反正一开始写更省事。

### 2.3 索引冗余

- **现状**：`ts`、`source`、`conv`、`is_me` 各一个单列索引。
- **做法**：按真实查询合并成复合索引（如 `(conv, ts)`），删掉用不上的。索引不是越多越好，每个都拖慢写入、占空间。
- **代价**：要用 `EXPLAIN QUERY PLAN` 看真实执行计划，别拍脑袋。
- **什么时候做**：记录几十万条、或插入明显变慢时。现在四个单列索引够用。

### 2.4 前端一次渲染上千条

- **现状**：P1 直接渲染最近 N 条（如 200 条）。
- **做法**：超过 500 条改用虚拟列表（只渲染可视区域），或「加载更多」按钮。
- **代价**：前端代码复杂度上升。
- **什么时候做**：手机上滑动明显卡顿时。200 条以内不会卡。

## 三、成本（用 DeepSeek 的钱）

### 3.1 每次问答都发全量人格提示词

- **现状**：系统提示词固定，每次请求都发。
- **做法**：把**固定不变的内容放最前面**（人格设定、规则），会变的内容放后面（检索片段、当前问题）。DeepSeek 有上下文缓存，命中的输入只要 0.02 元/百万 tokens，是未命中的五十分之一。
- **代价**：注意提示词顺序，几乎是零成本。
- **什么时候做**：P2 写 `persona.py` 时就按这个顺序拼，不要事后调。

### 3.2 检索片段塞太多

- **现状**：可能把搜到的 20 条全塞进上下文。
- **做法**：只取前 5 条，每条截断到 200 字；按字数预算倒着砍。单次请求控制在 3000 tokens 输入以内。
- **代价**：信息可能不够，答案变保守（这比编造好）。
- **什么时候做**：P2 一开始就这么写。

### 3.3 高峰时段调用

- **现状**：随时可能调。
- **做法**：非急用的批量任务（如给历史记录打标签、生成年度总结）放空闲时段跑，价格减半。
- **代价**：要写个能等的小调度，或者你手动挑时间。
- **什么时候做**：开始做批量处理时。

### 3.4 用大模型做小事

- **现状**：所有任务都调同一个模型。
- **做法**：结构化小任务（判断这条是不是广告、抽时间地点）用更便宜的模型或纯规则；只有「像不像你」这类才用好的。
- **代价**：多一套配置和分支。
- **什么时候做**：月账单超过 20 元时再琢磨。

## 四、人格像不像你

### 4.1 语气样本是随机抽的

- **现状**：随机抽若干条 `is_me = 1` 的发言当示例。
- **做法**：按场景选——对朋友、对家人、对同事各抽几条；再抽几条「短回复」（「嗯」「行」）和「长解释」。语气像不像，场景选对比数量重要。
- **代价**：要给会话分类（工作群/亲友），一开始手动标几个就够。
- **什么时候做**：P2 上线后你自己觉得「说话不像我」时，这是第一个该调的地方。

### 4.2 微调（LoRA）

- **现状**：不做。提示词 + 样本已经能到「像」的七八成。
- **做法**：攒够 3000 条以上**自己原创**的发言（不是转发的、不是表情包），云端租卡跑一次 LoRA，把权重挂到推理服务上。
- **代价**：租卡钱、几小时调参、之后每次换模型都要重训。而且数据量不够时效果是负的——会学成四不像。
- **什么时候做**：**满足三个条件才考虑**：自发言语料 > 3000 条、提示词方案已经调到极限、你确实在意最后那一两成。否则纯属浪费。

### 4.3 没有反馈回路

- **现状**：拟稿出了 2 条，你选一条改了发出去，系统不知道。
- **做法**：记录「采纳了哪条、改了什么」——采纳率是最直接的效果指标，改动的部分是最值钱的训练素材。
- **代价**：前端加个按钮，再加一张表。
- **什么时候做**：P2 用两周后，想知道「这功能到底有没有用」时。

## 六、代码结构

**现在不要做的事**（做了就是过度设计，等真痛了再说）：

- 不要加用户系统。一个人用，没有多用户就没有权限问题。
- 不要提前抽象「Repository 层」「依赖注入容器」。SQLite 一个文件，`store.py` 一组函数足够。
- 不要拆微服务。两个进程能解决的事，不值得上编排。
- 不要引入 Docker 到本机阶段。机器上连 WSL 都没有。

**该做的事**：

- 测试只覆盖关键路径：写入去重、两字检索、特殊字符、接口异常。不为 UI 写测试。
- 每个 service 函数控制在 30 行以内，超了就说明它管了两件事。
- 加新功能先想「能不能放进现有文件」，放不下再新建文件。文件数不是越多越好。

## 七、优化优先级（照这个顺序做）

| 顺序 | 做什么 | 触发条件 | 预计工作量 |
|---|---|---|---|
| 1 | 提示词前缀稳定、命中缓存 | P2 一开工 | 零 |
| 2 | WAL + keyset 分页 | P1 一开工 | 半天 |
| 3 | 检索片段裁剪到 5 条 | P2 一开工 | 零 |
| 4 | 语气样本按场景选 | 觉得说话不像你 | 一天 |
| 5 | 采纳率反馈 | P2 用两周 | 一天 |
| 6 | 两字词二元组索引 | 记录过十万且两字搜索变慢 | 两天 |
| 7 | 语义检索（向量） | 换说法搜不到成为常态 | 三天 |
| 8 | 话题段分块 | 导入历史后结果断章取义 | 三天 |
| 9 | LoRA 微调 | 上面全做完且仍不满意 | 一周 + 租卡钱 |

一句话：**1~3 是现在顺手就做的，4~5 是用了才会知道的，6 以后都是等痛了再说的。**

## 八、P4 备选：P2P 直连通道

> 由 [dsh-go](https://github.com/ccch1mneyyy/dsh-go) 的做法想到的一条旁路，**现在不做，只记下来**。它的远程连接用的是 [ds-harness-remote](https://github.com/liguobao/ds-harness-remote)（MIT）：两端建立 P2P 加密通道，打不通时用 TURN 中继，不需要公网 IP、也不用开放端口。

- **现状**：P4 计划是「香港轻量 2C2G + Caddy 域名 + HTTPS」，每月 35 元，备案在境外所以免了。
- **做法**：云服务器只作为「打不通时的中继」和一台常驻设备；电脑开着的时候，手机和电脑直接 P2P 通信，请求根本不进服务器。
- **代价**：要自己写一层适配（前端连的是通道而不是 HTTP 地址），至少 1~2 天；调试断线重连比调 HTTP 麻烦；多一个第三方组件的信任面。
- **什么时候做**：只有两种情况值得——① 每月 35 元都想省，且能接受电脑常开；② 隐私要求高到「提问和命中的记录连香港的服务器都不想经过」。否则 35 元买个省心更划算。

**不建议借的部分**：dsh-go 整体是 AGPL-3.0（只有 `sdk/`、`examples/` 是 MIT），抄它的代码会让整项目被迫开源；它用 Flutter 做壳、想在手机上跑后端，这两条都和本项目「Python 后端 + 网页前端」的方向相反。
